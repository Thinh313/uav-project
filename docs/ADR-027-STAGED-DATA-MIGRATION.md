# ADR-027 · Preserve evidence by migrating generations

Accepted UPDATE17. Sealed records cannot be rewritten to satisfy a new storage schema without changing the evidence identity. Add an explicit container schema2 with a typed, hash-bound migration catalog; stream independent copies of the three evidence stores into a new generation. Keep original layouts/records and all byte identities. No hardlinks between mutable generations or whole-project copies.

Candidate release is verified under current root roles but not selected while staging/canary runs. The source must be quiescent and remain unchanged through activation. Canary is loopback and rejects all mutation APIs, checks idle healthy stores and original record replay, then exits before byte rechecks. A durable activation intent precedes trust selection. If an interruption occurs before selection, explicit abort preserves the old selection. If trust selection already advanced, reconcile only forward with the exact confirmed intent and verified candidate/schema. Missing/corrupt bytes block both activation and reconciliation without deleting evidence. Retain original source and failed generation for inspection. Lock update maintenance and global trust while child runs; parent IPC governs application writers.

This is bounded engineering deployment, not an automatic internet updater or native/HeraHub installation. Layout catalog is a migration-time snapshot, not a perpetual current-content assertion. Controlled data cleanup and future revisions retain their existing provenance/acceptance contracts. Resource/OS service isolation and hostile administrator rollback remain separate target gates.
