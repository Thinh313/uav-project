L202:   * cite179†Package Manifest L203:   * cite180†Related Documentation L204:   * cite181†Legal Information L205: # Jetson Orin Nano Series, Jetson Orin NX Series, and Jetson AGX Orin Seriescite182†# L206: 
L207: This topic describes power and performance management features of NVIDIA^{®} Jetson Orin™ Nano series, Jetson Orin™ NX series, and NVIDIA^{®} Jetson AGX Orin™ series devices. It describes the power, thermal, and electrical management features visible to software, as well as some tools and related techniques.
L208: 
L209: Note
L210: The power management features of these devices are very similar, and most of this document applies equally to all. For convenience, the text often refers to them by the shorter name Jetson Orin. This term is used solely for convenience and is not a product name.
L211: Jetson Orin, Jetson Orin NX, Jetson Orin Nano, and NVIDIA^{®} Jetson™ Board Support Package (BSP) provide many features related to power management, thermal management, and electrical management. These features deliver the best user experience possible given the constraints of a particular platform. They help to create a user experience of:
L212: 
L213:   * Uniformly high performance
L214: 
L215:   * Excellent battery life
L216: 
L217:   * Perfect stability
L218: 
L219:   * Cool operation (the device is comfortable to touch)
L220: ## Interacting Featurescite183†# L221: 
L222: Power, thermal, and electrical management features place dynamic constraints on many operational settings (“knobs”), such as:
L223: 
L224:   * Clock gate settings
L225: 
L226:   * Clock frequencies
L227: 
L228:   * Power gate (or regulator enable) settings
L229: 
L230:   * Voltages
L231: 
L232:   * Processor power state (i.e., which idle state is selected for the CPU)
L233: 
L234:   * Peripheral power state (i.e., which idle state is selected for an I/O controller)
L235: 
L236:   * Chipset power state
L237: 
L238:   * Availability of CPU cores to the OS
L239: Some of these knobs are constrained by more than one feature. For example, `cpufreq` implements load-based scaling, which adjusts the CPU frequency according to how busy the CPU is. CPU thermal management, however, can override the target frequency of `cpufreq`. Consequently, before you attempt to debug power, performance, thermal, or electrical problems, you must familiarize yourself with all of the power, thermal, and electrical management features in BSP.
L240: ## Kernel Space Power Saving Featurescite184†# L241: 
L242: This section describes BSP features that save power and extend battery life. Many of these features are implemented by the Linux kernel, with support from firmware and hardware, and without significant involvement from the user space.
L243: ### Chipset Power Statescite185†# L244: 
L245: The supported power states are listed in order of increasing flexibility or configurability:
L246: 
L247:   * Off: There is only one way for a system to be off.
L248: 
L249:   * Deep Sleep (SC7) offers a small amount of configurability. For example, before entering Deep Sleep, the software can select which hardware wake events can wake the chip from Deep Sleep.
L250:   * Active state is extraordinarily flexible in terms of power and performance. It encompasses activity levels from low-power audio playback through peak performance. Power consumption in the Active state can range from tens of milliwatts to several watts.
L251: #### Supported Power Statescite186†# L252: 
L253: The supported power states are:
L254: Power State  | Characteristics
L255: --- | ---
L256: Off  | Power rails: None of the power rails supplying the SoC and DRAM are powered. State: No state is maintained in the SoC or DRAM. Exiting: Into Active state via cold boot.
L257: Deep Sleep (SC7)  | Power rails: `VDD_RTC`, `VDDIO_DDR`, `VDDIO_SYS`, and DRAM power rails are powered on. VDD_CORE and VDD_CPU are powered off. State: The SoC maintains a small amount of state information in the PMC block. DRAM maintains the state. Exiting: Into Active state via a predefined set of wake events.
L258: Active  | Power rails: `VDD_RTC`, `VDDIO_DDR`, `VDDIO_SYS`, `VDD_CORE`, and DRAM rails are powered on. Other power rails, including `VDD_CPU`, may be powered on. State: Software actively manages the power states of the devices that make up the SoC. Exiting: Software can initiate a transition from Active to any other power state.
L259: #### Power State Mapping to Linuxcite187†# L260: 
L261: BSP maps chipset power states to Linux power states as follows.
L262: 
L263: Chipset power state  | Linux power state  | Comments
L264: --- | --- | ---
L265: Off  | Off  | —
L266: Deep Sleep (SC7)  | Suspend to RAM  | The software can choose whether to enter Deep Sleep before the OS enters Suspend.
L267: Active  | Running/Idle (display on or off)  | Many SoC devices may be idle or disabled under driver control. For example, `VDD_GPU` may be powered off and the companion GPU may be power-gated.
L268: #### Deep Sleep (SC7)cite188†# L269: 
L270: If the systemd init system is being used, you can initiate deep sleep from the user space with the following command:
L271: 
L272:     $ sudo systemctl suspend
L273: 
L274: 
L275: You can also use the following command:
L276: 
L277:     $ sudo bash -c "echo mem > /sys/power/state"
L278: 
L279: 
L280: The first method of entering deep sleep is preferred because it cooperates better with systemd, which maintains the Linux runlevel. If your system is not running systemd, use the second method.
L281: The system can be awakened from deep sleep by common wake sources available on Jetson platforms:
L282: 
L283: Wake source  | Usage
L284: --- | ---
L285: Power button  | Press and release the power button on the Jetson device. If the power button is not available, connect and disconnect the power button pin and ground.
L286: RTC alarm  | Before entering low power state, program the RTC alarm with the following command:
L287: 
L288:     $ sudo bash -c "echo +10 > /sys/class/rtc/rtc<x>/wakealarm"
L289: where `<x>` is the RTC ID. The `rtc<x>` indicates the RTC used by system and can be found with the following command:
L290: 
L291:     $ find /sys/class/rtc/* -maxdepth 0 -printf "%f:" -exec bash -c \
L292:                "cat {}/hctosys" \; | grep :1 | cut -d: -f1 | head -n1
L293: USB type-C cable hotplug  | To flash the device, connect or disconnect a USB cable to the USB type-C port.
L294: USB remote  | Press any key on a USB keyboard connected to the device.
L295: Wake on LAN  | On another machine on the same LAN, enter:
L296: 
L297:     $ sudo etherwake -i <interface> <MAC_address_of_target>
L298: 
L299: 
L300: SD card detection  | Insert or remove SD card.
L301: ## Clock and Voltage Managementcite189†# L302: 
L303: Because clock frequency is proportional to voltage, dynamic voltage scaling is closely related to frequency scaling. For example, higher clock frequencies require higher voltages and vice versa.
L304: Most clock register manipulation on Jetson Orin is handled by the Boot and Power Management (BPMP) firmware, which runs on the BPMP processor. A Linux kernel driver on the CPU exposes a somewhat simplified view of the physical clock tree to software on the main CPU via the Linux Common Clock Framework.
L305: 
L306: Each of the significant clock domains on the chip has its own dedicated clock source, known as a Noise Aware Frequency Lock Loop (NAFLL).
L307: ### Regulator Frameworkcite190†# L308: 
L309: The Linux regulator framework provides an abstraction that allows regulator consumer drivers to dynamically adjust voltage or current regulators at runtime, without knowledge of the underlying hardware power tree.
L310: 
L311: The framework provides a mechanism that platform initialization code can use to declare a power tree topology and assign a driver that provides regulators for each node in the hardware power tree. Such a driver is called a regulator provider driver.
L312: BSP configures the platform power tree appropriately for Jetson Orin. Additionally, drivers within BSP act as regulator consumers, where appropriate.
L313: 
L314: When you port BSP to a new platform, you must ensure that:
L315: 
L316:   * The platform power tree is configured to match the underlying hardware.
L317: 
L318:   * All drivers for peripheral devices use the regulator consumer APIs correctly.
L319:   * The device tree and board configuration file information for your new platform avoid conflicts between functions using the same I/O pads. BSP drivers registering as regulator consumers can cause I/O pads on the chip to be unavailable for other functions.
L320: 
L321: The SoC core power rails (`VDD_CORE`, `VDD_CPU`, `VDD_GPU`, and `VDD_CV`) are under the direct control of the BPMP firmware. They are configured via the BPMP device tree blob (which is distinct from the Linux device tree blob).
L322: ## CPU Power Managementcite191†# L323: 
L324: The CPU power management strategy uses dynamic frequency scaling (DFS) with dynamic voltage scaling, idle power states, and core management tuned for the Jetson Orin architecture.
L325: ### Frequency Management with cpufreqcite192†# L326: 
L327: BSP implements CPU dynamic frequency scaling with the Linux `cpufreq` subsystem. The cpufreq subsystem comprises:
L328: 
L329:   * Platform drivers to implement the clock adjustment mechanism
L330: 
L331:   * Governors to implement frequency scaling policies
L332: 
L333:   * A core framework to connect governors to platform drivers
L334: 
L335: The policy for frequency scaling depends on which `cpufreq` governor is selected at runtime.
L336: For details, see the information at:
L337: 
L338:     <top>/kernel/3rdparty/canonical/linux-jammy/kernel-source/Documentation/admin-guide/pm/cpufreq.rst
L339: 
L340: 
L341: For each Jetson platform, NVIDIA selects a `cpufreq` governor and tunes it to achieve a balance between power and performance.
L342: 
L343: When a governor requests a CPU frequency change, the `cpufreq` platform driver reconciles that request with constraints imposed by thermal or electrical limits, and updates the CPU clock speed.
L344: Jetson Orin uses an NAFLL to clock each CPU. The NAFLLs are configured for Adaptive Voltage and Frequency Scaling (AVFS). Hardware, with the assistance of the BPMP firmware, ensures that the CPU voltage is appropriate for the NAFLL to deliver requested CPU frequencies.
L345: ### Idle Management with cpuidlecite193†# L346: 
L347: The Linux `cpuidle` infrastructure supports the implementation of SoC-specific idle states for each CPU core. `cpuidle` lacks direct support for idle states that are applicable to an entire CPU cluster or that extend beyond a CPU cluster.
L348: 
L349: For more information about the Linux `cpuidle` infrastructure, see:
L350: 
L351:     <top>/kernel/3rdparty/canonical/linux-jammy/kernel-source/Documentation/admin-guide/pm/cpuidle.rst
L352: #### CPU Idlecite194†# L353: 
L354: NVIDIA uses the generic upstream `psci_idle` driver that plugs into the `cpuidle` framework to enable CPU idle power management.
L355: 
L356: For each core there is an idle task that is scheduled when no other runnable tasks are left in that core’s run queue. This task places the core in a low-power state selected by the `cpuidle` governor. The core stays in that state until an interrupt wakes it up to process more work.
L357: When the last active core in a CPU cluster goes into an idle or offline state, the idle task puts the entire CPU cluster in a low-power state.
L358: #### Idle Statescite195†# L359: 
L360: The following table summarizes the supported CPU cores and the cluster idle states that are available on Jetson Orin and the BSP software.
L361: 
L362: Core states are denoted as Cx states, and cluster states are denoted as CCx states.
L363: 
L364: Type of state  | State  | Meaning  | Software support?

L404: #### Enabling or Disabling a Core Power State at Boot Timecite199†# L405: 
L406:   * To enable a core power state, set the following properties of the appropriate core state node:
L407: 
L408:     * status to `"okay"`
L409: 
L410:     * `min-residency-us` to a reasonable value
L411: For example, to enable power state C7 with `min-residency-us` = 5000:
L412: 
L413:     c7 {
L414:         compatible = "arm,idle-state";
L415:         state-name = "Core powergate";
L416:         wakeup-latency-us = <0x1388>;
L417:         min-residency-us = <5000>;
L418:         arm,psci-suspend-param = <0x40000007>;
L419:         status = "okay";
L420:         phandle = <0x83>;
L421:     };
L422: 
L423: 
L424:   * To disable a core power state, use either of the following procedures.
L425: 
L426:     * Remove or disable the appropriate core state node.
L427: 
L428: or
L429:     * Modify the appropriate core state node by setting the `min-residency-us` property to a high value, e.g., `0xffffffff`.
L430: 
L431: For example, to disable power state C7:
L432: 
L433:     c7 {
L434:         compatible = "arm,idle-state";
L435:         state-name = "Core powergate";
L436:         wakeup-latency-us = <0x1388>;
L437:         min-residency-us = <0xffffffff>;
L438:         arm,psci-suspend-param = <0x40000007>;
L439:         status = "okay";
L440:         phandle = <0x83>;
L441:     };
L442: #### Getting and Setting the Power State of a CPU Corecite200†# L443: 
L444: The pathnames of the nodes that represent core power states are:
L445: 
L446:     /sys/devices/system/cpu/cpu<x>/cpuidle/state<y>
L447: 
L448: 
L449: Where:
L450: 
L451:   * `<x>` is a core ID.
L452: 
L453:   * `<y>` is the index of the core power state: 0 for WFI or 1 for C7.
L454: 
L455: Note
L456: 
L457: A core power state’s status is 1 if the state is disabled, and 0 if it is enabled—the reverse of the usual Boolean sense of 0 and 1.
L458: To get the status of core power state `<y>` on core `<x>`, read the appropriate node. To set the status, write an ASCII 0 to 1 to the node.
L459: 
L460: Here are several useful commands for getting and setting the core power state:
L461: 
L462:   * To display the name of the core power state with index `<y>`, enter the command:
L463: 
L464:     $ cat /sys/devices/system/cpu/cpu<x>/cpuidle/state<y>/name
L465: 
L466: 
L467: For example, this command displays the name of state0:
L468: 
L469:     $ cat /sys/devices/system/cpu/cpu<x>/cpuidle/state0/name
L470:   * To get the status of core power state with index `<y>` on core `<x>`:
L471: 
L472:     $ cat /sys/devices/system/cpu/cpu<x>/cpuidle/state<y>/disable
L473: 
L474: 
L475:   * To change the status of core power state with index `<y>` on CPU core `<x>`:
L476: 
L477:     $ echo <b> > /sys/devices/system/cpu/cpu<x>/cpuidle/state<y>/disable

L496: ## Memory Power Managementcite202†# L497: 
L498: NVIDIA SoC chipsets include power saving features whose operation is largely invisible to software at runtime. Most of those features are statically enabled at boot, according to settings in the boot configuration table (BCT).
L499: Additionally, BSP implements Dynamic Voltage and frequency scaling for the memory controller (EMC/MC) and DRAM to save power. The EMC BCT and DVFS table are specific to the board design. The EMC DVFS table is included in the platform BPMP device tree file.
L500: ### EMC Frequency Scaling Policycite203†# L501: The following diagram illustrates the high-level memory interconnect topology from a hardware perspective:
L502: 
L503:     Memory interconnect topology:
L504: 
L505:                   +----+
L506:     +--------+    |    |
L507:     | TEXSRD +--->+    |
L508:     +--------+    |    |
L509:                   |    |    +-----+    +------+
L510:        ...        | MC +--->+ EMC +--->+ EMEM |
L511:                   |    |    +-----+    +------+
L512:     +--------+    |    |
L513:     | DISP.. +--->+    |
L514:     +--------+    |    |
L515:                   +----+
L516: Based on this topology, the kernel maintains a mirrored memory topology from a software perspective. The kernel adheres to the Linux Interconnect (ICC) framework, aggregates the memory bandwidth requirements from the clients, and transmits these requests to the BPMP to centrally manage the EMC frequency.
L517: 
L518: To inspect the requests made by individual clients, examine the following debugfs node:
L519: 
L520:     $ cat /sys/kernel/debug/interconnect/interconnect_summary
L521: The BPMP will collectively assess all requests from the clients and determine the most suitable EMC frequency to fulfill the Quality of Service (QoS) requirements.
L522: 
L523: For example, on the Concord platform, the CPU requests a minimum bandwidth requirement of 42,560,000 KBs, and the GPU requests a minimum bandwidth requirement of 136,512,000 KBs. To fulfill the demands of these two clients, the BPMP will select the highest converted EMC frequency that was derived from the bandwidth requirements.
L524: For the CPU, here is the converted EMC frequency from the bandwidth requirements:
L525: 
L526:     665 (MHz) = 42560000 (KB's) / 64 (BPC) / 1000
L527: 
L528: 
L529: For the GPU, here is the converted EMC frequency from the bandwidth requirements:
L530: 
L531:     2133 (MHz) = 136512000 (KB's) / 64 (BPC) / 1000
L532: 
L533: 
L534: The final EMC frequency will be 2133 MHz.
L535: In addition to the ICC requests input from the kernel, the BPMP will also factor in the current memory bandwidth usage information from the central actmon hardware. This information is crucial to determine whether the EMC frequency should be adjusted by scaling up or down. This process is referred to as central actmon DFS.
L536: Internally, the BPMP will compare the current memory bandwidth usage value against the boost-up threshold and the boost-down threshold. These threshold values are configured in the BPMP device tree file:
L537: 
L538:     bwmgr {
L539:             enabled = <0x1>;
