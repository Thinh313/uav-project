# P1 refinement decisions, after Android evidence

This adds implementation decisions to the pinned P1-TIP. It does not mark an AC passed or replace prior failures. Old APKs, sources and run evidence remain.

The initial competing Fly painters were an actual integration failure, reproduced by a separate QA module harness. The native operator projection now owns payload controls and labels. APK02 actual Android panel opening passed; this alone was not flight acceptance.

The aged preflight failure exposed an expensive full-history snapshot in status-only hot paths. Narrow getters preserve the same clock checks, full history and all limits. The original proxy-clock trace still fails identically in old/new offline replay. APK03 subsequently observed an aged preflight cohort of 1,624 ms. This is one scoped actual result, not an Android performance certification or a claim that cloning caused every prior delay.

Live camera/gimbal adjustment will use touch sliders, bounded steppers and explicit angle presets instead of text-number editors opening the Android IME over the cockpit. Presets and slider motion change requested values only; Apply is a separate explicit one-attempt intent. This preserves D1/D4/D5 and the same native ranges, units and authority checks. Main Fly shows a compact actual-media count; protocol intent counts remain in the panel. The failed IME-driven attempt is retained, not reclassified as a pass.

Generic EXPLICIT_SOCKET_CLOSE is insufficient fault evidence. A bounded first-domain-failure receipt will record the original stage, reason and source-age/delivery scalars before the same closure. It is UI/domain-reported diagnostic evidence, not a native clock attestation. No new per-frame journal flood, retry, grant, frame deletion or relaxed freshness is authorized. The 1,500 ms delivery and 3,000 ms cohort guards remain.

The route/geofence hypothesis for run01e was refuted: the actual typed radius was 150 m and native FENCE_STATUS reported no breach. No corpus coordinates, geofence parameter or geometry guard is changed to make that run pass. Its actual outcome remains interrupted/UNKNOWN, with observer-confirmed GCS failsafe and landing after common-link closure.

Actual APK04 run01f achieved the front-camera repeated workload while AUTO, then failed the JS flight-watch heartbeat freshness gate (1,853 ms). A newer heartbeat was already durable in native raw but not consumed by the JS domain; exact scheduling/filesystem root cause remains unknown. UI diagnostic journal reached its 2 MiB quota later, after closure, so quota exhaustion did not cause that first failure. The generation, raw and UNKNOWN review are retained.

A targeted causal cut is authorized: remove telemetry-paint-triggered full geometry scans from layout86 diagnostics. Keep explicit input/layout/startup/on-demand diagnostics durable under the same quotas and fsync. Flight rendering, native raw RX/WAL and its fsync-before-consumer/send, speedup1, 1,500/3,000 ms guards remain unchanged. Mock A/B must prove telemetry paint no longer triggers geometry scans and actual input still yields a fresh report. This cuts optional diagnostic work; it does not discard flight frames or prove a sole root cause. Build05 and actual acceptance require independent QA first.

The05 flight attempt exposed a confirmed native lifecycle race: an AUTO request was written at Android3236414 ms; a forward-sequence fresh GUIDED heartbeat at3236427 ms was immediately treated as an AUTO deviation. Distinguish AUTO_REQUESTED from AUTO_OBSERVED with a 1,500 ms transition deadline. Only the prior GUIDED mode is allowed while awaiting the first AUTO heartbeat; other modes or timeout fail closed. First observed AUTO locks normal deviation enforcement. ACK cannot promote this state. No retry, freshness relaxation or extra flight authority is authorized. Tests must preserve the failed raw and exercise deadline/other-mode/reversion negatives.

The initial Android harness incorrectly combined manager1001 configuration for front and center in one generation, conflicting with D3 ambiguous-key fencing. The frozen AC require repeated workload in one mission (A01), device2 proof (A05), and practical handover (A06), without requiring all manager requests in one generation. Independent QA confirmed this reading. Keep the same source fence and original KML: nominal exercises front repeated workload and front explicit consent; the separate loss generation exercises center manager/device2 setpoint followed by pending capture and link cut. Prior failures stay failures; receiver02 over-constrained distribution remains retained, receiver03 must explicitly record the corrected allocation.
