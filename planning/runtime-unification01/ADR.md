## Workspace publication boundary (independent QA counterexample)
QA source-extracted interleave `qa/workspace02/results.json` demonstrated that a UI/native/layout capture could later read a newly saved workspace in the snapshot worker. First49-input APK remains an artifact-only result, not runtime-qualified. Approved repair: an immutable versioned WorkspaceProjection built offUI and atomically published. Each coherent snapshot captures that same published projection with UI/native/layout and includes its version/SHA/original observation/pending-refresh provenance. It never labels an older projection as newest disk state. NativeSealed may expose the last published workspace while review refresh is pending; it cannot wait on slowreview. BOOTSTRAP READY must await the actual saved draft projection and actual rendered-version acknowledgement within the original request10s. All async commit callbacks keep source/process/view/foreground fences; no clock renewal or authority grant. No UI directoryscan. Linkdurable beforeownerstart remains required. One pure helper increases selected native inputs49->50; this is an enumerated source delta, not a resource cap change.

Normal Activity/WebView preparation is a product-owned resource step bounded60s within existing resource/emulator180s; it precedes public STATUS/BOOTSTRAP unchanged10s and never claims READY or authority from UI visibility.

One immutable candidate-attempt (maximum3 repaired candidates) may contain at most4 separately recorded cases: short, long and two fault cases. All share original5400s and aggregate budgets; testcases do not reset the repair-iteration counter.
